# GPU 库官方 UT 与功能修复（gpu_lib_test）

前提：构建已通过（gpu_lib_build 阶段完成）。本阶段产物：**UT 结果总表（通过/失败/跳过+原因）+ 已修复项清单（写入研究档案）**。

## 第一步：确认官方测试入口

从研究档案的盘查结论拿测试入口（盘问清单第 5 问）。注意区分：
- **官方测试**（test/、op_tests/、gtest）——本阶段只跑这些
- 库自带的**移植专用脚本**（如 aiter 的 test_ut.sh：维护者已筛选过本架构兼容项）——优先跑它，代表已知可行的基线
- benchmark 型测试（内置计时的）——记下时间数字，性能分析阶段复用

## 第二步：逐项跑（单个先行，再全套）

1. 先跑历史最快通过/最小的单项（冒烟）——验证"测试本身能跑"（依赖、环境、GPU 可见）
2. 再逐项跑全套，**每项记录**：名称、结果、耗时、失败输出前 20 行
3. GPU 测试注意：跑前 `rocm-smi` 查空闲；OOM 类失败先试缩小规模（很多测试脚本带规模参数）
4. 长测试设 timeout，区分"慢"与"挂"：挂住的测试（如 JIT 锁文件死等）单独记录症状

## 第三步：失败三分类（修复策略完全不同）

| 类别 | 特征 | 对策 |
|---|---|---|
| **环境类** | 依赖缺失、路径/权限、GPU 被占、版本不符、锁文件残留（JIT 库经典：root 属主锁文件导致 hang，删锁即解） | 修环境，不算库的 bug |
| **架构不支持类** | 错误信息含 MFMA/fp8/intrinsic/架构名；或该测试本身依赖被禁用的后端 | **预期失败**，标记 N/A（如 gfx1030 无 MFMA 的 CK 测试），不修 |
| **真 bug/真移植缺口** | 除上述外的断言失败、数值不对（allclose 不过）、crash | 进入修复循环 |

分类依据要落到证据（错误输出、涉及的源码路径），不靠感觉。

## ⚠️ 验证 harness 自身要先 sanity check（aiter 实测）

验证脚本的**参数顺序/语义错误会伪装成被测对象的 bug**：aiter 签名 `silu_and_mul(out, input)`，验证脚本写反成 (input, out) → "kernel 不落盘" 的假象，第一轮定位完全被误导。纪律：**先用最笨的已知输入过一遍 harness 本身**（如全 1 输入 + 恒等 kernel），确认 harness 能正确观察到正确行为，再开始测被测对象。

## ⚠️ 假 PASS 坑（aiter 实测）

测试脚本内嵌架构守卫（如 `SUPPORTED_GFX` 列表不含本架构时直接 return）会**静默 skip 却报通过**——特征：耗时异常短、与同类测试不成比例。识别法：抽查 2-3 个"通过"项确认 GPU 真的执行了工作（profiler 挂一次，或对比 host-only 任务的耗时量级）。aiter 实例：test_moe_sorting 报 PASS 2.6s，实际 SUPPORTED_GFX 守卫直接跳过，GPU 零执行。

## 第四步：修复验证循环

1. 定位：从失败输出回溯到源码（测试脚本 → 算子入口 → kernel）；源码级定位可派子代理（给它失败输出 + 研究档案作起点）
2. 修复原则：**最小改动**；优先在"适配层"修（架构守卫、类型映射、参数调整），不动算法核心；每处修复记录 症状→根因→改动→验证结果
3. **修一个验一个**：改完立刻重跑该项 + 跑一项相邻项（防回归）
4. 修不动的：记录根因分析 + 修复方案草案，标记待办（不要为凑通过率做危险修改）
5. 全部完成后重跑一遍全套确认无回归，更新结果总表

## 结果总表格式（写进研究档案）

```
| 测试 | 结果 | 耗时 | 失败类别 | 备注/修复 |
|---|---|---|---|---|
| test_xxx | ✅ | 12s | - | - |
| test_yyy | ❌→✅ | 45s | 真 bug | 根因…修复：文件:行 |
| test_zzz | N/A | - | 架构不支持 | 依赖 MFMA |
```

验收标准：[ ] 全套跑完有总表 [ ] 每个失败有分类与证据 [ ] 修复项有验证记录 [ ] 无回归。
