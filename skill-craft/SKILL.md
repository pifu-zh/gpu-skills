# Skill 工艺（skill-craft）

核心命题：**skill 是可传导的能力，不是文档**。写完的检验标准只有一个——一个没有先验知识的 agent 拿着它能不能做出专家级的产出。全流程六步，每步都有硬纪律。

## 步骤 1：意图捕获——从真实工作中提取，不从零想象

skill 的最佳素材是**已经做过至少一遍的工作流**：刚踩过的坑、重复写过的命令、被纠正过的错误。先回答三个问题：做什么（能力）、何时触发（description 的措辞素材）、产出什么形态。对话历史里用户给出的理念和纠正（"简单的事不要复杂做"、"XX 信息不要直接写进去"）是最高优先级素材——它们是用户亲手校准的纪律。

## 步骤 2：实测先行——没跑过的命令不配写进 skill

写进 skill 的每条命令、每个参数、每个文件路径，必须先在真机执行验证。验证过程本身就是素材库：踩的每个坑都变成坑表条目（坑表是 skill 最值钱的部分）。**禁止凭训练记忆写命令**——工具的默认行为、字段语义、版本差异（如 `-f csv` 不是默认值、字段名与文档不符）只有跑过才知道。

证据强度排序（对 skill 内容同样适用）：真机实测 > 官方文档 > 训练记忆。没验证的内容必须显式标注"未验证"，**禁止让猜测伪装成结论**。

## 步骤 3：层级起草——第一级最笼统，最后一级最具体

层级是**方向性原则，不是固定数量**。从 SKILL.md（最笼统）到实例数据（最具体），中间切几层由领域的"变化轴"自然决定——**同一层 = 适用范围相同的知识**（换了它才需要换的知识放同一层）：

- 单层：纯方法类 skill，一个 SKILL.md 装下（本文件就是）
- 两层：SKILL.md + references/（细节按需加载）
- gpu-perf 四层：领域恰好有三个变化轴——换软件栈（平台层）、换架构代号（架构层）、换机器（实例数据）——于是自然长出四层；换一个领域可能是三层或五层

切层时问：**这条知识换什么才失效？** 换平台就失效 → 平台层；换架构才失效 → 架构层；只有换具体机器/项目才失效 → 实例数据（不入 skill）。切不出清晰答案的知识别硬塞进某个层——放它实际归属的最笼统一层。

三条硬规则（与层数无关）：
- **具体与通用分离**：具体实例数据（某台机器的参数、某个项目的路径）和具体列举清单（厂商名、产品名）不进上层——上层留"位置"（模板+接入规则），不留名单。名单会过时，位置不会
- **模板代替空文件**：为未知的变体预留位置时，建一个 `_TEMPLATE.md`（含命名规则、接入流程、逐节问题清单），不为每个可能的对象预建空壳
- **宁少勿滥**：不写没验证的内容、不建用不上的文件、死内容发现即删；宁可 30 行全是有用信息，不要 300 行"完整性"

## 步骤 4：行文纪律——例子强于规则，解释 why 强于吼叫

- 指令式（"先跑探针"），不写 ALL-CAPS 和 MUST 堆砌——规则讲不清 why 才需要吼
- 每个反直觉的规则附一句为什么（附实测背书更强："实测：跨进程连跑 20 次时钟不爬升"）
- 标准化产出（报告、记录）给字面模板，照抄可用
- 报告脚本等重复性工具打包进 `scripts/`，不让人每次现写

## 步骤 5：盲测验证——skill 的能力要用无先验者证明

写完不算完，盲测通过才算 v1：

1. 选**已有已知答案**的真实任务（最好是 skill 建立过程中亲手做过的）
2. 派子代理执行，prompt 只含三样：skill 路径（"完整阅读并严格按其指引工作"）、任务本身、中性约束（临时文件清理等）。**零纠错提示、零方向提示、零坑位提示**——提示一个字就测不出 skill 的传导力
3. 多个任务占同一资源时**串行**派发（测量类任务并行会互相污染）
4. 评估四维：流程走通？坑表防住？归因/产出与已知答案一致？纪律执行（清理、不越界）？
5. 子代理带回的新知识**必须回写** skill——盲测的产出是双向的

## 步骤 6：使用-回写循环——skill 是活的

真实使用中发现的问题（字段语义坑、默认行为差异、流程卡点）当场回写坑表或流程；负结果也记录（排除的假设比猜测值钱）。每次回写问一句：这个坑属于哪一层？——放错层的知识会在换环境时变成误导。

## 与官方 skill-creator 的分工

官方流程覆盖通用步骤（意图→起草→测试→迭代）；本 skill 是用户校准的**硬纪律层**：层级规则、实测先行、盲测 SOP、具体/通用分离。创建 skill 时两者同读：流程走官方，纪律走本 skill。
