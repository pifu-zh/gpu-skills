# GPU 性能分析通用模型

**references 层级规则（skill 默认）：第一级最笼统，逐层下沉，最后一级最具体。**

```
L1 SKILL.md                    GPU 通用方法论（平台无关）
L2 platforms/<平台>.md          平台工具链（rocm.md / cuda.md / mojo.md / rust-cuda.md）
L3 platforms/<平台>/<架构>.md   具体架构（计数器语义、ISA 判读、工具支持矩阵、架构属性）
L4 项目本地 gpu-perf-baseline-<架构>.md   具体型号/这台机器（台账、实测基线、案例数字）
```

信息按层级就位：上一层只写下一层以上都成立的知识；往下查具体的，往上写通用的。L4 永不入 skill 目录。

方法论是平台无关的六阶段闭环，平台细节全部下沉。**开工第一件事：确认目标平台，然后读对应模块**（ROCm→`platforms/rocm.md`，NVIDIA→`platforms/cuda.md`，Mojo→`platforms/mojo.md`，Rust CUDA→`platforms/rust-cuda.md`；无对应模块时按本通用流程 + 该平台官方工具文档执行，探针脚本照跑）。

```
Phase 0 物理层基线 → Phase 1 环境匹配 → Phase 2 测量 → Phase 3 达标判定
                          ↑ 不达标：Phase 4 分层深挖 → Phase 5 优化循环（改一个变量→回到 Phase 2 复测）
```

核心纪律：**结论必须有测量数据支撑；每次只改一个变量；优化后必须用同一命令复测对比**。

**证据强度排序**（简单的问题不上重手段）：物理层实测（基线/时钟/传输量）> 编译器与驱动实证（反汇编、时钟还原）> 硬件计数器推断 > 纯计时推测。能用上一层证据回答的，不下探到下一层。分析用的临时产物放 /tmp 专用目录，用完即删。

## Phase 0：物理层基线（一切分析的地基）

先建台账，回答"这台机器极限在哪"。两层数据，缺一不可：

**理论规格（天花板）**：显存容量与类型、显存位宽→理论带宽、计算单元数×每单元通道数→峰值 FLOPS、最大/基础时钟、互联拓扑（PCIe 代数/通道数、卡间互联）。

**实测基线（地板，分析以此为准）**：spec 数字是有条件达成的理论上限，实测才能知道常态可达值——
- 可达带宽：跑带宽微基准（stream 大块拷贝/读写），记录 H2D/D2H/片内三个数
- 启动与传输延迟：空 kernel launch 耗时、小包 H2D 往返
- DVFS 行为：短 kernel 实际时钟 vs 最大时钟（爬升慢是常见测量陷阱）

探针脚本自动收集并打印基线报告：

```bash
python3 <skill目录>/scripts/gpu_probe.py              # 理论规格 + 环境检查
python3 <skill目录>/scripts/gpu_probe.py --bench PATH # 加跑带宽微基准（PATH=可执行文件）
```

基线报告要**保存下来**（建议 `<项目>/gpu-perf-baseline.md`），后续所有达标率都相对它计算。换驱动/换卡/超频后重跑。

## Phase 1：环境匹配检查（不匹配则测量无效）

按平台模块的检查清单执行，通用检查面：

1. **驱动 ↔ 运行时版本**：内核驱动版本是否在该运行时栈的支持矩阵内
2. **架构支持**：GPU 架构代号是否被当前工具链/编译器/分析工具支持（例：消费级卡常被专业分析工具排除在外——这类"工具装了但用不了"必须在测量前发现）
3. **设备可见性与权限**：设备节点存在、进程有访问权限、容器场景设备直通完整
4. **计数器支持**：分析工具的硬件计数器通道对本架构可用（`gpu_probe.py` 会查）
5. **时钟策略**：性能模式/时钟是否被限制（功耗墙、散热、调度策略）
6. **被测程序的编译级别**：确认程序以预期优化级别编译（CMake `CMAKE_BUILD_TYPE` 为空 = -O0）。分析一个 -O0 程序测出的是编译器的锅，不是程序的性能——任何归因在此之前都无效（盲测实证：试炼场全部示例曾以 -O0 编译，ISA 病态主导了一切测量）

任何一项不匹配：先修复或换通道，并在报告里声明测量受限。

## Phase 2：测量（热点定位 + 定性）

两步走，命令查平台模块。**先做价值筛选**：数据规模 KB 级、无迭代循环的"API 演示型"程序不进测量流程——它的耗时由启动开销支配，测出的达标率没有意义（一句话记录即可）。有真实负载才继续：

1. **时间线全景**：采集 kernel/传输/API 三个维度的时间线，生成热点汇总表（ROCm 用打包脚本 `scripts/gpu_profile_report.py`；其它平台用等效工具：nsight systems / 平台 profiler）。产出：按 GPU 时间排序的热点 kernel 列表 + memcpy/API 开销占比。
2. **计数器定性**：对热点 kernel 采硬件计数器，拿四类证据：指令混合（计算/访存/共享内存指令数）、访存量（实际字节数）、占用率（在板 wave 与理论上限之比）、利用率（各子单元 busy%）。

读数要点：先看占比不看绝对值（<5% 时间的 kernel 不值得优化）；`运行时内部 kernel`（如 ROCm 的 `__amd_rocclr_*`）算在传输/运行时头上；计数器高 busy ≠ 高吞吐（见平台模块的解读陷阱）。

## Phase 3：达标判定（% of peak 是核心语言）

对每个热点 kernel 计算**实测吞吐 ÷ Phase 0 实测基线 = 达标率**，并先确认该 kernel 类型的**可达天花板**（不同类型天花板不同，90% 不是万能线）：

| kernel 类型 | 可达天花板（相对实测基线） | 说明 |
|---|---|---|
| streaming 访存（连续读写） | ~90%+ 峰值带宽 | saxpy/归约/拷贝类 |
| 分块复用（GEMM/tiling） | 80-95% 峰值算力（算力受限时） | 数据复用好，逼近计算极限 |
| gather/scatter、稀疏访问 | 远低于 50%（天然低） | 随机访存受延迟主导，先修访问模式再谈达标 |
| 小 kernel / 短任务 | 受启动开销与 DVFS 支配 | 先测开销占比和实际时钟 |

判定逻辑（用户标准：**常规算法在具体机器上有空间提到 90% 以上；达不到就是有原因可查**）：

- 达标率 ≥ 该类型天花板 → **达标**，报告并停止（或作为回归基准）
- 达标率 < 天花板 → 进入 Phase 4 深挖，锁定原因层次

结论报告模板（每次分析照此输出）：

```
## GPU 性能分析：<程序/算法名>
- 基线：<卡名>/<架构>，实测带宽 <..> GB/s，实测峰值算力 <..>（<时钟> MHz 下）
- 环境：驱动/运行时版本，匹配检查 <通过/受限项>
- 热点：<kernel> 占 <x>%（<n> 次，avg <t>）
- 关键指标：吞吐 <..>（= <带宽/算力> 的 <..>%，天花板 <..>%）· 指令混合 · 占用率
- 判定：<达标 / 不达标→原因层次>
- 下一步：<达标→作为基准固化 / 不达标→Phase 4 哪一层>
```

## Phase 4：不达标深挖（四层归因，从上往下排查）

按"改动代价从小到大"排序，锁定第一层出问题的：

1. **算法与数据布局层**：计算量与访存量的比值是否就到不了天花板（冗余读、无复用、数据结构导致随机访问）？证据：实际访存字节数 ÷ 最小必需字节数 > 2× → 访存冗余是主因。先改算法/布局（tiling、合并、SoA/AoS、向量化结构），这一层收益通常最大。
2. **kernel 代码层**：占用率低（寄存器/LDS 用量挤占在板 wave）？访存未合并（同 warp 相邻线程访问不相邻地址）？共享内存 bank conflict？同步过密？证据：占用率 <25%、共享内存/全局访存指令比异常、细化到源码行的采样。
3. **编译器层**：目标架构 flag 是否显式且正确（否则按通用目标生成劣化 ISA）；循环是否向量化（ISA 里有无宽访存指令）；寄存器分配是否 spill（查 scratch/spill 符号）；该内联/展开的是否做了。**证据 = 反汇编**：`--save-temps`（或等效）保留中间产物，反汇编热点 kernel 对照源码看生成质量——不看反汇编的编译器调优都是猜。
4. **驱动/运行时层**：时钟策略被限（性能模式/功耗墙）？拷贝走了低效通道（可搬数据用错了引擎）？调度/同步开销占比高（kernel 太碎、过多小传输）？证据：时钟实测 vs 上限、传输引擎口径、API 时间线。

每一层结论都要有该层证据，禁止跳层归因（"感觉是驱动问题"不是证据）。

## Phase 5：优化循环

```
选最高优先证据 → 改一个变量 → 重新 Phase 2 测量 → 对比达标率 → 记录
```

- 每轮产出一行对比记录：`改动 | 指标变化 | 达标率 前→后`
- 收敛（连续两轮提升 <2%）或达标 → 停，写总结报告
- 改动没起作用也要记录——负结果排除了一个假设，比猜测值钱
